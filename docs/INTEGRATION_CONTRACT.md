# 遊戲端串接契約

這份契約用來防止後續把「能載入的 DLL」誤當成「功能完成」。所有遊戲狀態修改都必須在伺服器端執行。

## 建築辨識

- 只處理 `TryGetMapObjectId()` 回傳 `PRF_EggResourceProcessor` 或 `PRF_ResourceBreedingFacility` 的模型。
- 即使暫時共用原版 Blueprint class，也不得改變同 class 的原版大型孵化器或古代孵化場。
- 找不到必要反射函式時整個功能保持停用，不能退回會產生一般帕魯的原版取得流程。

## 孵化攔截

- 完成孵化後保留原版產生的實際後代資料，但禁止呼叫會把後代送入帕魯終端的玩家取得流程。
- 工作項目以不可變 ID 對應蛋、孵化結果、支解處理與獎勵提交。
- 36 級建築整條流程最多兩個未完成工作項目；只有存在足夠完整空位時才可消耗蛋糕。蔬菜蛋糕必須一次保留兩個空位。
- 載入舊存檔時先還原階段與已提交 ID，再允許任何 tick 執行。

## 支解結算

- 不建立世界帕魯、不建立支解傳送帶角色欄位，也不播放逐隻送入動畫。
- 必須使用原版產生的完整後代資料，呼叫原版支解機實際使用的機率結算。`GetDropItemData()` 只是讀取掉落資料，不能用 MOD 自行擲骰代替原版支解。
- 不複製掉落表、不自行重寫機率，也不額外提高數量或稀有率；原版支解自身適用的世界設定、被動判定與排除規則交由原版處理，不能由 MOD 猜測並刪除。
- 2026-09-06 09:11:46 的 UE4SS 日誌已確認：原版單顆孵化器完成的後代保存資料，接入非場景個體參數並呼叫 `UPalDatabaseCharacterParameter::GetMeatCutItemInfo_withProbability` 成功。14:41:08 的單蛋入庫測試另確認扣蛋與兩種材料各 3 個入庫；使用者也確認正常退出重進後結果保留。這不代表多蛋、崩潰一致性或自製建築已通過。
- 原版結算一次後保存不可變結果；兩座機器都使用原版支解機的地面物品生成流程，在前方出口出料，允許原版搬運帕魯接走。不掃描箱子挑選直接入庫目標，不因箱子容量或過濾設定阻止出料。
- 提交成功才寫入 committed ID；重送相同 ID 必須無效果，等待期間不得重新擲骰。原版掉落生成要求是非同步的，必須區分要求送出與實際物品建立；目前單蛋測試的 `GROUND_REQUESTED` 只代表前者，遇到中斷禁止重發。

## 容器與 UI

- 26 級：54 格唯寫入蛋倉；不設材料輸出倉。
- 36 級：1 格蛋糕白名單、2 格不可見孵化位；不設材料輸出倉。
- 玩家 UI 不提供取回、換位、取消與取得孵化帕魯按鈕。
- 建築拆除先封鎖互動與 tick，再清除所有容器／工作項目，最後只交由原版返還建材。

## 上線閘門

在下列項目全部通過前不得裝入主要存檔：

1. 反射函式在目前遊戲版本實機解析成功。
2. 單人新測試世界完成放蛋、停電、前方掉落、玩家拾取、帕魯搬運、無箱子／箱子不接收、拆除及重載。
3. 主機端與加入端確認不重複產生材料。
4. 專用伺服器確認伺服器重啟後不重複提交獎勵。
